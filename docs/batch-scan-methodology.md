# 多目标批量检测方法

本文说明 v0.2.2 如何把多个模型/路由的重复测试组织成可复核的本地证据。它补充通用的
[评分方法](methodology.md)，不改变题目的标准答案或评分规则。

## 能回答什么，不能回答什么

批量检测回答的是：“在题包、评分规则、入口、模型路由、推理档位和运行条件都可核对的前提下，
本机记录到的端到端表现怎样，是否与自己的匹配历史一致？”

它不能直接回答底层实际使用了哪个未公开模型，也不能证明提供商改变了服务端。网络、客户端版本、
CLI 版本、账号策略、工具调用、上下文管理和模型本身都会影响端到端结果。因此页面使用“稳定”“观察”
和“证据不足”等证据标签，不把一次低分包装成 IQ 测量或服务端“降智”事实。

## 证据组与可比性

一个批次只能属于一个执行轨道：

- 客户端辅助：ChatGPT 或 Claude，由用户在每题的新空白会话中复制题目并粘贴完整回答；
- 自动 CLI：Codex CLI 或 Claude Code，在独立临时工作区中运行固定项目题。

客户端和 CLI 使用不同题型、交互方式与隔离边界，必须分成两个 cohort（证据组）。即使界面上出现同名
模型，也不能把两个轨道的分数放进同一基线或直接比较。客户端当前只支持快速批次；标准和完整批次只
用于 CLI。

同一证据组内，每个目标都绑定以下身份：目标类型、请求模型、模型来源、推理档位、推理档位来源、
题包 ID/版本/内容哈希、评分规则版本，以及执行入口身份。CLI 入口还绑定 provider family、适配器契约、
可执行文件来源类型和规范化版本；路径、token 和登录输出不进入公开身份。

### 模型名称的三个层次

结果页分别显示：

1. 请求模型：用户或 CLI 参数明确请求的模型；
2. 可见模型：客户端界面或 CLI 安全输出实际展示的名称；
3. provider default：未固定具体模型、由提供商默认路由决定。

`default` 只描述路由方式，不代表工具知道底层模型。自动识别若超时、未公开或有多个候选，会失败关闭
并要求人工确认，不会猜一个名称。识别与 `--version` 探测都是本地只读操作，不发送模型请求。

## 模式、重复次数与硬上限

费用政策版本 1 把每种模式的最大范围写进批次确认哈希。开始前会显示按实际目标数计算的任务启动数、
最大 provider turns、任务预算、预计/最大时长和授权失效时间。下表是允许的全批次硬上限，不是承诺
一定消耗这么多：

| 轨道与模式 | 最多目标 | 每目标重复 | 最多成员运行 | 启动/人工交互上限 | provider turns 上限 | 任务预算上限 | 执行窗口 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 客户端快速 | 4 | 1 | 4 | 32 次人工交互 | 32 | 4,320 秒 | 4 小时 |
| CLI 快速 | 4 | 1 | 4 | 8 次任务启动 | 160 | 14,400 秒 | 8 小时 |
| CLI 标准 | 4 | 3 | 12 | 24 次任务启动 | 480 | 43,200 秒 | 24 小时 |
| CLI 完整 | 5 | 5 | 25 | 50 次任务启动 | 1,000 | 90,000 秒 | 72 小时 |

首次确认有效期为 15 分钟。任一计数超出一单位都会在创建数据库记录或接触执行入口之前被拒绝。
订阅 token/配额无法从这些本地上限可靠换算，因此显示为未知；谁在自己的客户端或 CLI 中运行，谁承担
自己的订阅用量。CI 只使用本地假入口，模型请求数为零。

快速模式用于验证流程和发现明显差异，只有一个样本时不能声称具有重复性。标准模式提供三次 CLI 重复，
适合观察波动。完整模式提供五次 CLI 重复，并且是唯一允许建立历史基线和计算回归信号的模式。

## 调度、隔离与暂停

批次计划先冻结再执行。调度器按目标平衡成员顺序，避免把某个目标固定在所有测试的开头或结尾。
每个客户端题要求新空白会话；每个 CLI 任务在独立临时工作区运行。视觉矩阵只是已验证记录的视图，
不是评分或调度的事实来源。

同一时间最多执行一个 CLI 成员。配额、认证、网络等可恢复基础设施故障会把当前成员标为 deferred，
调度器可继续其他目标。恢复必须显示新的预算并取得明确授权；授权绑定批次、成员、失败类别、尝试次数、
预算和失效时间。恢复复用原 run ID，不静默创建第二个样本，也不自动扩大预算。

程序在 reserved、launching 或 running 阶段退出时会在下次启动对账。未越过 provider boundary 的预留
可以安全复用；已经可能发出请求的成员不会自动重放，而会中断或暂停等待决定。取消会阻止未开始成员，
已越过边界的进程先进入终止流程，不能伪装成从未调用。

## 评分、样本数与无效结果

所有成员仍使用密封题包的确定性评分器。结果矩阵的每个格子显示实际进入该统计量的样本数，并可展开
成员、任务类别、排除原因和来源信息。不能从颜色或格子位置反推不存在的数据。

配额、认证、网络、工具不可用等基础设施失败作为无效证据排除；受控超时、turn 上限或输出预算耗尽属于
agent-budget failure，表示模型在事先固定的预算内没有完成，会按评分规则处理。取消、缺失、非有限数值、
身份不一致或证据不完整都失败关闭，不能进入分母或基线。

批次使用中位数汇总重复运行，并显示中位绝对偏差（MAD）描述离散程度。类别保持等权，避免题数较多的
类别自动获得更大权重。任务级明细只在身份完全匹配时展示差值。

## 完整模式的历史基线

完整批次创建时原子冻结基线快照，后续完成的批次不能倒灌进本轮基线。校准政策版本 1：

- 只查看候选批次创建之前 90 天内的历史；
- 每个 UTC 日期只选同条件下最新的完整批次，最多 12 个；
- 至少需要 5 个匹配历史完整批次，并覆盖至少 3 个 UTC 日期；
- 候选目标至少需要 5 个有效成员；
- 用固定种子做 2,000 次批次/运行级 bootstrap，报告 95% 差值区间；不会把同一次运行里的多道题
  当作相互独立样本。

匹配采用失败关闭。目标轨道、路由身份、推理档位、题包哈希、评分规则、适配器/入口身份或隔离状态不一致
的历史都会排除。候选本身及候选之后的数据也会排除。页面和公开导出显示入选数量、UTC 日期数、排除
计数和基线快照哈希，便于复核“基线究竟用了什么”。

## 信号含义

当前生产政策使用 5 分绝对下降、8% 相对下降和 95% 区间作为保守门槛，但信号不是只看一个阈值：

- 证据不足：没有可计算分布，或快速/标准模式不做基线判定；
- 观察：已有差异但样本门槛不足，或结果尚不能稳健归为稳定；
- 稳定：绝对下降不超过容忍值的一半，且置信区间不支持超过容忍值的下降；
- 很可能退化：设计上要求样本充分、绝对下降至少 5 分、相对下降至少 8%，且 95% 区间上界仍低于
  -5 分。

“很可能退化”在 v0.2.2 的生产政策中明确保持关闭，直到真实用户校准和独立的统计/安全复核完成。
因此当前完整批次只会给出稳定、观察或证据不足。任何信号都只描述本工具的匹配端到端证据，不是对
提供商内部模型的事实裁决。

## 历史、导出与删除

历史页把客户端和 CLI 批次分开，并保留题包哈希、规则版本、入口来源、运行状态和基线兼容性。公开批次
JSON 是单独的严格 schema，只允许聚合结果、版本、内容哈希、样本数、排除原因、不确定性和方法元数据；
它不包含 run ID、本地路径、原始回答、完整日志、登录信息或 token。未知字段会被拒绝。公开导出不是
完整备份，也没有导入/恢复承诺。

删除批次默认只解除批次与运行的关联。用户明确选择后，才会删除该批次拥有的单次运行；活动批次拒绝
删除。文件删除采用持久待办、隔离重命名、数据库事务提交、最终清理四步流程。若中途退出，启动对账会
在数据库仍存在时恢复文件，或在提交已完成时清理隔离区，避免留下半删除证据。完整本地备份保留批次
外键与哈希并执行一致性检查，但不应当作为公开报告分享。

更多操作问题见[故障排查](troubleshooting.md)，数据暴露边界见[隐私说明](privacy.md)与
[安全说明](security.md)。

## 如何解读一次异常

先核对格子的样本数和排除原因，再核对 requested/visible/default 路由、推理档位、题包哈希、版本和
clean/resumed 状态。快速模式异常应当用相同条件重复，而不是立刻下结论；标准模式可以观察 CLI 波动；
完整模式出现“观察”时，应继续积累跨日期的匹配历史并检查基础设施变化。不要为了得到想要的信号而
删除低分、改阈值、混用客户端与 CLI，或把失败重试当作独立样本。
